# Legacy UI Policy & Evaluation Guide

> **STANDING DIRECTIVE**: *Existing UI is implementation history, not necessarily design authority.*

---

## 1. The Core Policy

Aldriva has evolved through multiple phases of rapid engineering. Some pages and components were built as functional prototypes or generated by AI tools before a mature design system was codified.

As an AI engineer working on Aldriva:
1. **Preserve Business Logic & Data Flow**: Never break server actions, database relationships, RLS policies, routing, checkout steps, or verification gates.
2. **Do NOT Blindly Copy Visual Layouts**: Just because an existing page has 4 metric cards, a noisy gradient header, and generic table borders does not mean new pages should copy that layout.
3. **Freely Redesign Presentation When Touching a Page**: When fixing, extending, or building a feature, you are empowered to improve information architecture, spacing, visual hierarchy, and component composition according to the Aldriva Design System.

---

## 2. When to Redesign vs. When to Preserve

| Scenario | Action |
|---|---|
| Modifying an existing page that looks generic/cluttered | **Redesign presentation**: simplify containers, improve typography, apply standard tokens, maintain all data and actions. |
| Building a new feature or page | **Design from scratch using Aldriva tokens**: do not copy legacy layout templates; structure the page around the user's primary goal. |
| Working on core functional backend/logic | **Preserve**: do not touch working UI files unless requested or required by the task scope. |
| Fixing a bug on an existing page | **Minimal surgery**: fix the bug cleanly, ensure tests pass, avoid sprawling visual refactors unless the task asks for it. |

---

## 3. The 9-Question UI Evaluation Checklist

Before implementing or modifying any user interface, ask:

1. **What is the user trying to accomplish on this page?** (e.g., approve a pending article, purchase a ticket, check payout balance).
2. **What is the single most important piece of information?** (Ensure it has dominant visual hierarchy).
3. **What is the primary action?** (Make the primary CTA obvious, singular, and solid orange).
4. **What can be removed without losing functionality?** (Eliminate redundant badges, duplicate stats, decorative icons).
5. **What can be combined?** (Consolidate scattered metadata into unified rows or summary bars).
6. **Which containers are strictly necessary?** (Remove nested card-in-card patterns and redundant borders).
7. **Which existing primitives should be reused?** (Check `components/ui/` and `components/dashboard/` first).
8. **What should be redesigned to look cleaner?** (Tables with better padding, forms with logical groupings, clear empty states).
9. **What happens on mobile (375px)?** (Ensure critical actions remain reachable, tables scroll horizontally or collapse into clean cards).
