## 1. Core Architectural Decisions

### ADR-0001: Marketplace Ownership, Entitlements, and Dual Payment Rails
- **Decision Date**: 2026-07-11
- **Status**: Shipped & Active
- **Key Tenets**:
  - All user-owned content (`articles`, `businesses`, `products`) enforces a non-nullable `owner_id` (or `seller_id`) FK referencing `auth.users(id)` `ON DELETE CASCADE`.
  - Optional affiliations (`organizer_id`, `business_id`) are separate nullable FKs, not polymorphic columns.
  - Entitlements are directly represented as a verified status on the resource itself (e.g., `status = 'active'`), flipped exclusively by verified payment webhooks.
  - Aldriva operates as the **sole merchant of record** across credit/debit card (Stripe) and cryptocurrency (NOWPayments) payment rails. No Stripe Connect or third-party seller accounts are used.

### ADR-0002: AI Output Validation as a Permanent Structural Requirement
- **Decision Date**: 2026-09-01
- **Status**: Shipped & Active
- **Key Tenets**:
  - LLM models are never trusted to self-police against prompt injection, data leaks, or instruction bypasses.
  - Every AI tool must use a hard-coded safe column projection (`SAFE_COLUMNS`) in its database query — `SELECT *` is strictly prohibited.
  - Every string generated by the AI model must pass through `guardBeforeDisplay()` (`lib/ai/output-guard.ts`) before being rendered in the admin UI or dispatched to external publishing channels (e.g., Facebook Graph API).
  - Flags and rejections must be persisted to the `ai_guard_rejections` audit table and surfaced to administrators at `/admin/ai/rejections`.

### DEC-0003: Canonical Tenant & Entity Unification (`organizers.id`)
- **Status**: Shipped & Active (`migration_48`, `migration_58`, `migration_59`, `migration_62`)
- **Key Tenets**:
  - Rather than creating separate tenant tables for every vertical, `organizers.id` serves as the canonical Entity / Tenant root identifier.
  - Access delegation is governed by `entity_members` with standardized roles (`owner`, `admin`, `manager`, `editor`, `finance`, `viewer`).
  - RLS policies enforce multi-tenant isolation via the `is_entity_member(tenant_id, roles)` Postgres helper function.

### DEC-0004: Next.js 16 Pre-Stream Status Gate in `proxy.ts`
- **Status**: Shipped & Active (`proxy.ts`)
- **Key Tenets**:
  - Next.js 16 App Router streaming flushes HTTP 200 headers before downstream server component `notFound()` handlers execute.
  - Gated content checks (articles, business listings, digital products, external events) are executed inside `proxy.ts` via lightweight REST queries before streaming commences.
  - Unentitled or non-existent resources are rewritten to `/_not-found` with an explicit `404` header.

### DEC-0005: Three-Tier Client Separation
- **Status**: Shipped & Active
- **Key Tenets**:
  - Client components must use `lib/supabase.ts` (browser client enforcing RLS).
  - Server components and user-authenticated actions must use `lib/supabase-server.ts` (user cookie context).
  - Service-role privileges (`lib/supabase-admin.ts`) are restricted to privileged backend routines, webhook handlers, and background crons, and must never be imported into client components.

### DEC-0006: Offline Door Scanner with Deterministic Conflict Resolution
- **Status**: Shipped & Active (`lib/offline-scanner.ts`, `migration_122`, `migration_124`)
- **Key Tenets**:
  - Event door check-in must function even in venues with zero cellular or Wi-Fi connectivity.
  - Scanner clients cache ticket rosters locally in IndexedDB (`idb`).
  - Scans recorded offline are synced in batches upon reconnection. Timestamp-ordered check-in logs and `ticket_checkin_conflicts` resolve concurrent multi-door entries safely.

### DEC-0007: Private Storage Delivery for Digital Goods
- **Status**: Shipped & Active (`migration_116`, `lib/digital-products.ts`)
- **Key Tenets**:
  - Digital products (e-books, files, tickets) must never be stored in public storage buckets.
  - Deliverables reside in the private `product-assets` bucket.
  - Access is mediated exclusively by server-verified entitlement checks generating short-lived signed URLs (~120s TTL).

### DEC-0008: POS Integration Strategy (Integrate & Normalize, Don't Replace)
- **Status**: Established Principle (for Phase 11)
- **Key Tenets**:
  - Physical businesses frequently possess existing POS hardware (Square, Clover, Toast).
  - Aldriva provides integration adapters to ingest and normalize sales, inventory, and menu items across channels rather than forcing merchants to abandon existing hardware.

### DEC-0009: Tenant Website Eligibility & Canonical Entity Scope
- **Status**: Shipped & Active (`migration_125_tenant_websites.sql`)
- **Key Tenets**:
  - `tenant_websites.tenant_id` references `organizers.id` (1:1 with unique constraint).
  - Any organizer type (`business`, `nonprofit`, `restaurant`, `creator`, etc.) is eligible to provision a tenant website.
  - No database-level restriction or CHECK constraint binds tenant websites exclusively to `businesses`; any vertical-specific feature gating occurs at the application layer.

### DEC-0010: Owner-Membership Seeding Behavior on Future Bulk Imports
- **Status**: Recorded Principle / TODO
- **Key Tenets**:
  - The current trigger `trg_organizers_seed_owner` seeds `entity_members` with `role = 'owner'` when `organizers.user_id` is present.
  - When an admin bulk-import or CLI seeding path for organizers/businesses is eventually constructed, the import script must explicitly verify or seed corresponding `entity_members` rows if running in contexts where `auth.uid()` is null.

### DEC-0011: RLS Privilege Segregation & Destructive Action Gating
- **Status**: Shipped & Active (`migration_126_website_delete_rls_fix.sql`)
- **Key Tenets**:
  - Broad `FOR ALL` database RLS policies on multi-tenant entity resources are prohibited when privilege tiers distinguish content authors (`editor`) from entity managers (`owner`, `admin`, `manager`).
  - Destructive actions (`DELETE`) on tenant websites, pages, and navigation trees are strictly reserved for `ENTITY_ROLES_MANAGE` (`owner`, `admin`, `manager`) and platform administrators.
  - Database policies must be explicitly segregated into `FOR SELECT` (all entity members), `FOR INSERT` / `FOR UPDATE` (`ENTITY_ROLES_CONTENT_WRITE`), and `FOR DELETE` (`ENTITY_ROLES_MANAGE` only).
  - Server action authorization checks (`lib/actions/website.ts`) must mirror this privilege segregation at the application tier.

### DEC-0012: Hermetic Static Analysis Testing Convention for Database RLS & Migrations
- **Status**: Established Project Convention & Testing Architecture
- **Key Tenets**:
  - The repository's automated test suite (`npm test`, executed via Node test runner) operates hermetically without requiring an active live PostgreSQL database socket connection or external network dependencies.
  - Database security rules (RLS policies, privilege grants, security definers, triggers) are tested via strict structural static analysis, AST verification, and migration source invariant assertions (consistent across `lib/security/__tests__/p0-rls-policies.test.cjs`, `lib/ai/__tests__/tenant-architecture.test.cjs`, and `lib/__tests__/website-foundation.test.cjs`).
  - Application-level authorization boundaries (e.g. role gates in server actions and API handlers) are verified via static code analysis and in-memory pure logic tests.
### DEC-0013: Trigger Function Security Context for Auto-Created Organizer Entities
- **Status**: Shipped & Active (`migration_127_ensure_business_organizer_security_definer.sql`)
- **Key Tenets**:
  - Functions invoked via triggers to auto-provision platform entities (such as `ensure_business_organizer()` auto-generating an `organizers` shell row upon business creation) must execute as `SECURITY DEFINER` with a pinned, secure search path (`SET search_path = public, pg_catalog`).
  - This prevents least-privilege column-level `INSERT` grants on `organizers` (enforced since `migration_103`, which intentionally revokes direct caller access to internal/invariant columns like `is_business_auto_created`) from causing `42501 permission denied` errors during entity creation.
  - Safe by design: `ensure_business_organizer()` is only invoked by the internal `BEFORE INSERT` trigger on `businesses`, cannot be directly invoked with arbitrary arguments, sets `user_id` strictly from `NEW.owner_id`, and sets `is_business_auto_created` unconditionally to `true`.

### DEC-0014: Server-Side Embed Block Resolution & No Cross-Tenant `owner_id` Fallback
- **Decision Date**: 2026-09-18
- **Status**: Shipped & Active (`lib/website-embeds.ts`, Phase 3)
- **Context**: The public website rendering engine embeds live tenant data (events, products, fundraisers) in public site pages. These embed resolvers could run client-side (via SWR/fetch) or server-side (awaited in async Server Components). Products on the Aldriva platform do not have a direct `organizer_id` FK on the `products` table — they are linked via `businesses.organizer_id → products.business_id` (two-step join).
- **Key Tenets**:
  - Embed resolvers (`resolveEventsEmbed`, `resolveProductsEmbed`, `resolveFundraiserEmbed`) must execute server-side using `createSupabaseAdmin()` (service-role). This avoids exposing service-role credentials or unsanitized tenant data to browser clients, and keeps embed query logic within the trusted server environment.
  - `tenantId` is **never** sourced from block JSON. It is injected from `tenant_websites.tenant_id` fetched by the server route, preventing a tenant from spoofing another tenant's ID via crafted page content.
  - `resolveProductsEmbed` **must not** use `owner_id` as a fallback when no business is linked to a tenant. An `owner_id` query is scoped to a user, not a tenant, and a user may own businesses across multiple organizer accounts. If no business is linked to the current tenant (`organizer_id`), the resolver returns `[]`. This eliminates a structural cross-tenant product leak path.
  - LIMIT must be clamped server-side: `Math.min(Math.max(1, block.limit ?? 6), 12)`. Block JSON must not be able to trigger unbounded queries.

### DEC-0015: `sanitizeUrl()` Reuse as Single Write-Time & Render-Time URL Validation Layer
- **Decision Date**: 2026-09-18
- **Status**: Shipped & Active (`lib/website-blocks.ts`, Phase 3)
- **Context**: Block JSON validation at write-time (when a block is saved) and URL attribute sanitization at render-time (when HTML or anchor hrefs are output) could each maintain their own URL safety logic, risking them drifting out of sync as rules evolve.
- **Key Tenets**:
  - `validateBlock()` in `lib/website-blocks.ts` calls `sanitizeUrl()` from `lib/sanitize-html.ts` directly for all URL fields (`href`, `src`, `videoUrl`, `mapUrl`) rather than reimplementing a separate regex.
  - `BlockRenderer.tsx` also calls `sanitizeUrl()` at render time before emitting any anchor `href` or image `src`.
  - This creates a single source of truth for URL allowlisting rules: dangerous schemes (`javascript:`, `data:`, `vbscript:`), protocol-relative URLs (`//...`), and length bounds are enforced once and inherited at both layers.
  - Any future change to `sanitizeUrl()` logic (e.g., adding a new dangerous scheme) automatically applies to both validation and rendering without requiring a parallel update.

### DEC-0016: Code-Owned Immutable Template Registry (Phase 3 — Stages A–C)
- **Decision Date**: 2026-09-21
- **Status**: Shipped & Active (`lib/website-template-registry.ts`, `lib/website-category.ts`, `lib/website-templates.ts` shim)
- **Key Tenets**:
  - Canonical website templates are code-owned, immutable, and versioned (`id@version`, e.g. `restaurant-delight@1.0.0`). No `website_templates` DB mirror is created at this stage (deferred to marketplace/analytics when needed).
  - Template schema is complete-website shaped (`metadata + theme/header/footer + pages[] + navigation`), not `defaultBlocks: Block[]` alone. Multi-page support is part of the schema from day one.
  - Legacy `business-starter`, `restaurant-delight`, etc. are preserved via compatibility shim in `lib/website-templates.ts` (maps `TEMPLATE_REGISTRY` home page blocks to `WEBSITE_TEMPLATES.defaultBlocks`), so existing creation flows continue to work.
  - Version bump creates a new `id@version` entry; existing `id@version` rows are never mutated after a website has been created from them (immutability guarantee).

### DEC-0017: Stable Block & Item IDs + Section Envelope (Phase 3 — Stage B)
- **Decision Date**: 2026-09-21
- **Status**: Shipped & Active (`lib/website-blocks.ts`, `components/dashboard/website/builder/defaultBlocks.ts`, `components/dashboard/website/builder/builderReducer.ts`, `lib/actions/website-builder.ts`)
- **Key Tenets**:
  - Every block/section carries a stable `id: UUID` (`BaseBlock` extends `Partial<SectionEnvelope>`). Repeatable items (`features.items`, `gallery.images`, `testimonials.items`, `faq.items`, `about.highlights`) also carry stable `id: UUID`.
  - `normalizeBlock` / `normalizeBlocks` idempotently backfill missing ids for legacy JSONB data without altering semantic content; `cloneBlockWithNewIds` assigns fresh ids on duplication (builder `DUPLICATE_BLOCK`).
  - Strategy is application-level normalization, not a mandatory data migration. `validateBlock` preserves `id` and envelope (`visible`, `spacing`, `background`, `hiddenOnMobile`) when present and valid; `parseBlock` fallback also preserves envelope.
  - Builder reducer normalizes on `SET_BLOCKS`/`ADD_BLOCK` and on `getPageBuilderData`/`savePageDraft` so draft and publish paths both operate on id-stable data. No `type-index` identity remains for history/reorder/AI operations.

### DEC-0018: Business Category vs Website Template Family (Phase 3 — Stage C)
- **Decision Date**: 2026-09-21
- **Status**: Shipped & Active (`lib/website-category.ts`, `db/migration_130_website_category_and_metadata.sql`, `lib/actions/website.ts`, `app/dashboard/org/[id]/website/new/NewWebsiteClient.tsx`)
- **Key Tenets**:
  - Business category (what the org is, authoritative `organizers.org_type` plus optional `businesses.category`) and website template family (how the site is presented) are distinct. Business category may map to multiple template families.
  - No duplicate taxonomy is created. `mapOrgTypeToWebsiteCategory` and `refineWebsiteCategoryFromBusinessCategory` derive `WebsiteCategory` from existing fields (`organizers.org_type` CHECK: `nonprofit|business|restaurant|...`). Compatibility is centralized in `lib/website-category.ts` (`isTemplateCompatibleWithCategory`, `getCompatibleTemplates`).
  - `tenant_websites.metadata JSONB` (migration 130) stores `websiteCategory` (and future `templateId/templateVersion`) without adding a dedicated column per concern. No RLS change; GIN index on `metadata`. Existing rows default to `'{}'`.

### DEC-0019: Atomic Website Creation with CreationRequestId Idempotency (Phase 3 Stage E)
- **Decision Date**: 2026-09-24
- **Status**: Shipped & Active (`db/migration_131_website_atomic_creation.sql`, `lib/actions/website-instantiation.ts`, `lib/website-hydration.ts`)
- **Key Tenets**:
  - Website + pages + drafts + navigation are created in a **single transaction** (`BEGIN; … COMMIT;` + `EXCEPTION WHEN OTHERS THEN RAISE;`). No partial state on failure.
  - Concurrency race boundary is `INSERT … ON CONFLICT (tenant_id) DO NOTHING` + `RETURNING id INTO v_inserted_website_id`; concurrent retries do not rely on `SELECT-before-INSERT`.
  - Idempotency is `metadata->>'creationRequestId'` (`crypto.randomUUID()` per `NewWebsiteClient` request) compared after conflict (`v_existing.metadata->>'creationRequestId' = v_request_id` → `idempotent:true`; otherwise `23505`).
  - RPC is `SECURITY DEFINER` with pinned `search_path=public,pg_temp`, `REVOKE ALL FROM PUBLIC, anon, authenticated`, `GRANT TO service_role` only. Application authorizes via `getCurrentUser` + `requireTenantContext` (owner/admin/manager) before `supabaseAdmin.rpc`.
  - Hydration is **whitelisted** (`ALLOW_HYDRATION_FIELDS` 6 fields, `TOKEN_MAP` `{{organizer.name}}` etc.) and executed **before** RPC (`cloneBlockWithNewIds` → `normalizeBlocks` → `hydrateBlocks` → `validateBlocks`). No external fetch/file upload inside transaction. No `tax_id`/sensitive column leakage.

### DEC-0025: Public image media on Cloudflare R2
- **Decision Date**: 2026-10-08
- **Status**: Implementation approved; migration and live R2 verification pending.
- **Key Tenets**:
  - Raw uploads go to a separate private bucket (`R2_TMP_BUCKET`) with no public domain. Processed images only go to public `R2_BUCKET`; temporary paths are never created in the public bucket.
  - R2 helpers accept a bucket parameter. Final public URLs use `MEDIA_BASE_URL`; temporary objects never receive public URLs.
  - Only allowlisted, intentionally public image purposes are accepted. SVG decoding is blocked; Sharp re-decodes, applies orientation, strips metadata through WebP re-encoding, and limits dimensions to 2000×2000.
  - CMS uploads require an active platform admin; tenant purposes require existing tenant membership roles. Media metadata is RLS-protected; API service-role writes follow these checks.
  - Existing Supabase image flows, private buckets, video, and audio remain unchanged. Migration 157 is canonical in `db/` with a timestamped Supabase mirror.

### DEC-0026: Server-only boundaries for secret-reading modules
- **Decision Date**: 2026-10-08
- **Status**: Shipped & Active
- **Key Tenets**:
  - Secret-reading modules and server-only helpers carry `import "server-only"`; mixed modules are split so client components import only browser-safe helpers, types, and constants.
  - Tests alias the package to an empty local stub. The markers remain in application code; standalone scripts and test fixtures are intentionally not marked.
