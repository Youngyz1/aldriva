# Rollback Considerations

The safest rollback strategy for this migration is **don't delete the old project** until well past the point of confidence:

1. **Keep the old (production) Supabase project fully intact and paused-not-deleted** for a defined bake period (recommend at least 2–4 weeks, or one full billing cycle, past cutover) after traffic moves to the new project. Supabase allows pausing a project without deleting data; this is nearly free insurance against needing to reverse the migration.
2. **DNS/app-config rollback is the actual rollback mechanism** — since the app itself doesn't change (only its Supabase env vars), reverting `NEXT_PUBLIC_SUPABASE_URL` / keys / Stripe webhook target back to the old project's values is the entire rollback procedure, *provided* no new data was written to the new project that isn't also reflected in the old one. This is why freezing writes on the old project before final sync (see `04-data-migration-strategy.md` §5) matters: it defines the exact point past which the two projects diverge and rollback becomes lossy.
3. **Once real user writes land on the new project post-cutover, rollback is no longer free.** Any donations, ticket purchases, new signups, or comments made against the new project after cutover would need to be manually replayed into the old project to roll back cleanly. Treat the cutover as effectively one-way past a short grace window unless you've built explicit forward-sync tooling (out of scope here) — communicate this clearly before pulling the trigger on cutover.
4. **Stripe webhooks are the sharpest edge**: if a webhook fires against the new project's endpoint for a payment that only exists in the old project's `donations`/`ticket_orders`/`product_orders` tables (e.g. a race during cutover), that payment's status update is silently lost. Freeze Stripe webhook delivery to the old endpoint and confirm the new endpoint is live and tested *before* the DNS/env-var flip, not after. See `07-stripe-and-payment-fields.md` for the full list of payment-state columns this affects.
5. **Storage objects are not versioned by this migration** — if a storage object is overwritten or deleted on the new project post-cutover, there's no automatic way to recover it from the old project's copy unless the old project's storage is also kept intact during the bake period (which pausing rather than deleting the old project provides).
6. **This migration reproduces production behavior exactly, including the RLS/storage/function observations documented in `RECOMMENDATIONS.md`.** Those are not migration blockers and are explicitly out of scope for cutover — do not let "we're doing a migration anyway" turn into an uncontrolled behavior change bundled with cutover, since that makes it much harder to isolate the cause if something breaks post-cutover. If any recommendation is adopted, apply it as a separate, individually-verified change *after* the bake period referenced in item 1, not during it.

See `RECOMMENDATIONS.md` for the full list of non-blocking observations found during the audit, kept separate from this migration's scope by design.
