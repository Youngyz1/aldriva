# Phase 3 — Courier GPS, Early Dispatch, and Tracking

**Status:** Phase 3 source changes are local. The owner reports migration 192 was applied on staging and its postchecks passed; this session did not independently query the database. Courier map rendering changes are local and still need deployed staging/device acceptance.

## Investigation

- The app-wide `Permissions-Policy` set `geolocation=()`. This denies the browser Geolocation API at the document policy layer, which can appear as a permission denial even when the user's Chrome and device settings allow location. The app had no code path to distinguish browser permission denial from unavailable position, timeout, insecure context, or failed upload.
- The rider dashboard acquired GPS only during the later delivery statuses. Dispatch offers were created only when an order became ready, despite an existing `estimated_ready_at` field.
- The existing path stores authenticated rider coordinates in `order_delivery_locations`; customer tracking reads the newest row through the order's bearer tracking token. The business dashboard had no scoped rider-location endpoint. Existing views poll; no push provider or database realtime client is wired for this flow.
- `components/delivery/DeliveryMap.tsx` uses Leaflet 1.9.4 and raster tiles; `app/globals.css` imports Leaflet CSS, and the map container has an explicit height. The owner reports the public OSM tile server returned HTTP 403. Source inspection also found the prior CSP `img-src` omitted OSM tile hosts, so both provider response and CSP were possible contributors; no browser capture was available to independently distinguish them.
- The `organizers` schema and `orders` schema store no business/customer latitude and longitude. `order_delivery_locations` contains courier coordinates, and `events` has separate event coordinates. Current courier/customer/manager map callers pass only the authorized courier point. Pickup and destination pins therefore remain unavailable until the existing business and delivery-address workflows capture verified coordinates; text addresses are not converted to invented pins.
- A standalone `OSRMProvider` exists in `lib/routing/osrm-provider.ts`, but no delivery map/API calls it and no `OSRM_ROUTING_URL` configuration is present. It defaults to the public OSRM demo service and falls back to Haversine geometry, which is a straight segment, so it is not treated as an available road route or ETA. The UI continues to state that road-route ETA is unavailable.

## Implementation

- The same-origin Permissions Policy now permits geolocation. Rider GPS starts only after an explicit action, distinguishes permission/position/timeout/connectivity states from backend upload state, supports retry/resume, and cleans up its watcher. Uploads are limited to at most one per 12 seconds unless the rider moves at least 25 metres; the server additionally rate-limits and validates timestamps and ownership.
- Authenticated courier location writes require an active assignment to that courier and an active delivery status. The endpoint rejects malformed, too-old, too-far-in-the-future, and non-monotonic timestamps. Customer reads are scoped to that tracking token's order; business reads require tenant authorization and the exact assigned courier. Responses are not cacheable, and stale locations are identified.
- Migration 192 creates durable offers in the order transaction once a delivery enters accepted/preparing/ready with a saved preparation estimate. It offers to batches of five eligible couriers with a configurable 1–60 minute response window (10-minute default), advances to the next eligible batch from the authenticated courier feed, reconsiders accepted/preparing orders when a rider completes a delivery, and exposes a manager retry action. Claiming is locked/atomic, preserves the kitchen's current order status, and only returns the destination after the courier wins. The pre-claim feed omits the customer's precise destination. A guarded rollback is included.
- `db/tests/migration_192_postcheck.sql` contains read-only checks for the owner to run after manual staging application.
- Existing courier/customer polling remains the update transport. The rider sees the pickup location and preparation-ready time before pickup; the order status is preserved until kitchen and courier actions advance it. Customers see the assigned rider's first name early, while the rider's phone number is exposed only after pickup. Business users with tenant access can see the assigned rider's last location/freshness and retry stalled dispatch.
- The shared Leaflet map now requests the documented [TomTom Orbis v2 raster tile endpoint](https://docs.tomtom.com/map-display-api/documentation/tomtom-orbis-maps/v2/raster/raster-tile) using 256px PNG tiles at zoom levels 0–22. The browser key comes from `NEXT_PUBLIC_TOMTOM_API_KEY`; the value is never logged. CSP `img-src` allows only `api.tomtom.com` for this provider, and the map displays TomTom/OpenStreetMap attribution. Missing keys and failed tile loads show separate, actionable states. Existing loading/retry, validated-coordinate initialization without a fallback city, incremental marker updates, courier follow/recenter controls, drag-to-stop-follow behavior, and `ResizeObserver`/orientation invalidation remain. Courier, customer, and manager screens continue choosing pickup versus delivery stage from order status. The current data model still cannot provide either stop's coordinates, so only the rider marker can appear until that data is added through an approved workflow.

## Limits and owner actions

- Migration 192's staging application and successful postchecks are owner-reported. This session did not connect to the database and did not reapply the migration.
- The offer timeout defaults to 600 seconds and can be changed to 60–3600 seconds by an authorized database operator through the `courier_dispatch_settings` singleton (for example, set `offer_timeout_seconds = 900` for 15 minutes); resetting it to 600 seconds is required before running the guarded rollback.
- Initial dispatch is transaction-triggered and does not require an open browser. Cohort timeout advancement is currently invoked by courier-feed polling; there is no scheduled background worker. If all courier sessions are closed, later cohorts advance when a courier feed is next opened. A production durable worker/cron requires an approved hosting/runtime configuration.
- The existing app has no push/email notification channel for courier offer, assignment, preparation-time change, or ETA mismatch events. Offers persist in the rider feed, and the normal polling views refresh state; no notification delivery is claimed.
- `NEXT_PUBLIC_TOMTOM_API_KEY` is configured in the local `.env.local`; its value was not displayed. The current TomTom pricing page lists 200,000 monthly raster tile requests free, with usage-based pricing beyond included usage. Account entitlement, Vercel staging configuration, tile responses, and deployed browser rendering still need verification. No TomTom tile request, deployment, or billing change was made in this follow-up.
- ETA/preparation mismatch alerts and road routing are not implemented. TomTom raster requests use the existing TomTom account; usage beyond its included allowance may incur usage-based charges.
- Desktop/mobile Chrome, deployed staging, tile network requests, and full end-to-end lifecycle have not been verified in an authenticated browser or physical device in this work session.
